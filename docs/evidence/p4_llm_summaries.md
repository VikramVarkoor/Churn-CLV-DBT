## Reading this result

All four summaries passed verification: every number cited matches a number in that segment's
own JSON entry (within the tolerance documented in `python/llm/verify.py`), no summary
mentions a segment it shouldn't, and none uses causal language. That is what the verifier was
built to check, and it checked cleanly against a real LLM's real output, not just the stub.

One real limitation the verifier does not catch, found by actually reading the output rather
than just trusting the pass/fail flag: segments 1 and 2 both describe `mean_monetary_net` as
"average purchase value" ("an average purchase value of $10,314.83", "an average purchase
value of $826.25"). That number is each customer's mean total net spend over their whole
purchase history up to the cutoff, not the average size of a single order (that would be
`avg_basket_value`, a field that isn't given to the model at all here). A marketing reader
could reasonably misread "$10,314.83 average purchase value" as "this segment's typical order
is worth ten thousand dollars," when the real claim is "this segment's typical customer has
spent ten thousand dollars in total." The verifier's three checks are about whether a number is
supported and whether the language is causal or references a real segment; they say nothing
about whether the model's own description of what a number represents is accurate. This is a
real gap in this phase's design, not a bug in the code that ran -- the numbers themselves are
exactly right, and the prompt (`python/llm/prompts.py`) gives the field its literal name
(`mean_monetary_net`) but never defines it in plain language, leaving the model to guess at an
exact phrase. A fix for a later iteration would be to either give the model a one-line
definition of each field in the prompt, or add a fourth verifier check for specific banned
mischaracterizations of known fields -- neither was built here, since task #16's fixtures and
this phase's scope were defined against the three checks docs/design.md locked before this
real run happened, and semantic mislabeling wasn't one of them.

Segment 3's and segment 0's summaries avoid this specific wording ("spend about $1,865 each",
"spend around $327.46" -- both ambiguous but not explicitly claiming "per purchase"), so this
is not a wholesale failure of the prompt, just an inconsistency in how the model chose to
phrase the same field across different calls at temperature 0. (Temperature 0 makes a single
call deterministic; it does not make four separate calls describe the same field name the same
way.)
